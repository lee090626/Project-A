# 🤖 Drilling RPG 통합 개발 가이드 (Master Development Guide)

이 문서는 Drilling RPG 프로젝트에서 에이전트가 따라야 할 작업 원칙, 금지사항, 검증 절차의 기준입니다. 프로젝트 구조와 현재 구현 지식은 `docs/`와 실제 소스 코드를 정본으로 봅니다.

---

## 🧭 0. 에이전트 작업 원칙 (Agent Operating Principles)

이 원칙은 LLM 기반 에이전트가 흔히 만드는 과잉 구현, 추측성 수정, 불필요한 리팩토링을 줄이기 위한 기본 행동 규칙입니다. 사소한 작업에서는 속도와 균형을 맞추되, 불확실성이 있으면 속도보다 명확성을 우선합니다.

### 0.1 구현 전 사고
- 가정을 명시하고, 불확실하거나 해석이 여러 개인 경우 먼저 사용자에게 확인합니다.
- 더 단순한 접근이 있으면 제안하고, 요청이 과도하거나 위험하면 근거를 들어 조정합니다.
- 혼란스러운 요구사항을 숨기지 않고 무엇이 모호한지 구체적으로 밝힙니다.

### 0.2 단순성 우선
- 요청받은 기능 이상을 만들지 않습니다.
- 단일 사용처를 위해 불필요한 추상화, 확장성, 설정 옵션을 추가하지 않습니다.
- 구현이 과하게 커졌다면 더 작은 해법으로 줄입니다.

### 0.3 외과적 변경
- 요청과 직접 관련된 파일과 라인만 수정합니다.
- 인접 코드 정리, 포맷 변경, 리팩토링은 요청 없이는 하지 않습니다.
- 기존 스타일을 따르고, 관련 없는 죽은 코드는 발견해도 삭제하지 않고 언급만 합니다.
- 자신의 변경으로 생긴 미사용 import, 변수, 함수는 제거합니다.

### 0.4 목표 기반 실행
- 작업을 검증 가능한 목표로 바꾸고, 다단계 작업은 짧은 계획과 검증 방법을 먼저 제시합니다.
- 버그 수정은 원인 분석, 재현 또는 검증 기준, 수정, 확인 순서로 진행합니다.
- 기능 변경 후에는 변경 범위에 맞는 타입 검사, 테스트, 빌드, 문서 갱신 여부를 확인합니다.

## 🏛️ 1. 설계 철학 (Design Philosophy)

모든 개발 작업은 소프트웨어 공학의 3대 핵심 원칙을 기반으로 수행됩니다.

1.  **관심사의 분리 (SoC)**: 비즈니스 로직, UI, 데이터 저장은 완전히 분리되어야 합니다. UI 컴포넌트는 오직 렌더링에만 집중하며, 복잡한 상태 관리나 비즈니스 연산은 외부 훅이나 시스템으로 추출합니다.
2.  **높은 응집도 (High Cohesion)**: 하나의 파일이나 모듈은 하나의 책임만 완벽히 수행합니다. "함께 변경되어야 하는 데이터와 로직은 하나의 단위로 묶는다"는 원칙을 고수하여 무분별한 파편화로 인한 **산탄총 수술(Shotgun Surgery)**을 방지합니다.
3.  **낮은 결합도 (Low Coupling)**: 시스템 간의 의존성을 최소화합니다. 시스템 간의 직접적인 참조나 상호 호출을 금지하고, 가능한 인터페이스나 이벤트 기반의 메시지 전송 시스템을 활용하여 유연성을 확보합니다.

## ⚠️ 2. 절대 금기 사항 (Strict Don'ts)

1.  **God File / God System 생성 금지**: 하나의 시스템 내에 대미지 연산, 보상 획득, 시각 효과 등 서로 다른 관심사를 섞는 것을 엄격히 금지합니다. 발견 시 즉시 관심사별 원자적 단위(Atomic Unit)로 분해해야 합니다.
2.  **God Manager / 순환 참조 금지**: 매니저(Manager)나 시스템(System) 간에 서로를 직접 호출하거나 의존하는 구조를 만들지 마세요. 소통은 반드시 **이벤트 버스나 옵저버 패턴을 통한 구독/발행 형태**를 지향해야 합니다.
3.  **직접적인 DOM 접근 금지**: 게임 엔진은 Web Worker 환경에서 실행됩니다. UI 레이어를 제외한 곳에서 `window`나 `document` 객체를 절대 참조하지 마세요.
4.  **임시 이미지(Placeholder) 외부 링크 금지**: 이미지가 필요할 경우 `generate_image` 도구를 사용하며, 외부 URL은 절대 사용하지 마세요.
5.  **FSD (Feature-Sliced Design) 아키텍처 위반 금지**: 레이어 간 단방향 의존성 규칙(Upper → Lower)을 엄격히 준수하세요.
6.  **도메인 API 문서화**: 외부에서 재사용되는 도메인 함수, 타입, 인터페이스에는 JSDoc을 작성합니다. 단순 내부 헬퍼에는 과도한 주석을 추가하지 않습니다.
7.  **UI 스타일 제약**: 현대적이고 정갈한 디자인을 위해 `italic` 및 `uppercase` Tailwind 클래스 사용을 금지합니다.

## 🏗️ 3. 시스템 아키텍처 확인 기준 (Architecture Reference)

아키텍처의 상세 정본은 `docs/ARCHITECTURE.md`, `docs/CORE_GAME_LOOP.md`, `docs/RENDERING_PIPELINE.md`와 실제 소스 코드입니다. 이 문서에서는 에이전트가 지켜야 할 판단 기준만 정의합니다.

- **FSD 레이어 유지**: `app/`, `widgets/`, `features/`, `entities/`, `shared/`의 단방향 의존성 규칙을 위반하지 않습니다.
- **Worker 경계 유지**: 게임 엔진 로직은 Web Worker 경계를 기준으로 UI와 분리합니다.
- **ECS 책임 분리**: `System`과 `Component`의 책임을 섞지 않고, 새 로직은 관련 시스템의 기존 역할과 실행 순서를 확인한 뒤 추가합니다.
- **소스 우선 검증**: 문서와 코드가 다르면 현재 동작은 소스 코드를 기준으로 판단하고, 관련 문서를 갱신합니다.

## 📝 4. 코딩 및 네이밍 규칙 (Coding Standards)

### 4.1 명명 규칙 (Naming)
- **디렉토리**: `kebab-case` (예: `game-engine`)
- **로직 파일 (.ts)**: `camelCase` (예: `physicsSystem.ts`)
- **컴포넌트 (.tsx)**: `PascalCase` (예: `InventoryWindow.tsx`)
- **변수 및 함수**: `camelCase` (`handleUpgrade`)
- **타입 및 인터페이스**: `PascalCase` (`PlayerStats`)
- **상수**: `SCREAMING_SNAKE_CASE` (`MAX_ENTITIES`)

### 4.2 코드 작성 지침
- **JSDoc 기준**: 외부에서 재사용되는 도메인 함수, 타입, 인터페이스에는 JSDoc을 작성합니다.
- **Type Safety**: `any` 사용을 지양하고, `npx tsc --noEmit`으로 타입 안정성을 수시로 확인합니다.
- **논리 패턴**: 조기 리턴(Early Return)을 활용하여 들여쓰기 깊이를 최소화합니다.

## 🌿 5. Git 전략 및 GitHub 협업 규칙 (Git & GitHub)

### 5.1 브랜치 명명 규칙
- **형식**: `{type}/{issue-number}-{description}`
- **예시**: `feat/12-shop-upgrade-logic`, `fix/45-worker-memory-leak`

### 5.2 커밋 컨벤션 (Conventional Commits)
**Conventional Commits** 표준을 엄격히 준수하며, 상세 설명은 반드시 **한글**로 명확하게 작성합니다.
- `feat`: 새로운 기능 추가
- `fix`: 버그 수정 (로직, 렌더링 오류 등)
- `docs`: 문서 수정 (README, 가이드 문서 등)
- `style`: 코드 포맷팅, 세미콜론 누락 등 (비즈니스 로직 변경 없음)
- `refactor`: 코드 리팩토링 (기능 변화 없이 구조만 개선)
- `perf`: 성능 개선 및 최적화
- `test`: 테스트 코드 추가 및 수정
- `build`: 빌드 시스템, 외부 의존성 관련 변경
- `ci`: CI 설정 파일 및 스크립트 수정
- `chore`: 패키지 매니저 설정, 기타 사소한 작업
- `revert`: 이전 커밋 되돌리기
- `rename`: 파일/폴더 이름 변경 또는 위치 이동

#### 5.2.1 커밋 단위 규칙
- 하나의 커밋은 **하나의 목적(문제 해결/기능 추가/리팩토링 1건)**만 포함합니다.
- 서로 다른 성격의 변경(예: `feat` + `refactor`, 로직 변경 + 대규모 포맷 변경)은 반드시 분리 커밋합니다.
- PR 본문에는 커밋별 단위를 요약하여 리뷰어가 커밋 단위를 즉시 파악할 수 있어야 합니다.
- `git commit` 메시지 작성 시 `-m` 옵션 반복 사용을 금지합니다. (여러 줄 본문이 필요하면 커밋 템플릿/에디터를 사용)

### 5.3 작업 프로세스 (Two Track)
이슈, 브랜치, 커밋, PR 작업은 사용자가 요청했거나 승인한 경우에 수행합니다. 사용자가 코드 수정만 요청한 경우에는 작업 범위에 맞는 검증까지 수행하고, 임의로 커밋하거나 PR을 만들지 않습니다.

1. **표준 트랙 (Standard Track)**: 사용자가 이슈/PR 기반의 중요 작업을 요청한 경우
   - `gh issue create`를 통해 이슈 생성 및 번호 할당.
   - 브랜치 생성 및 단계별 구현.
   - 각 단계마다 변경 범위에 맞는 타입 검사, 테스트, 빌드를 수행합니다.
   - 커밋이 요청된 경우 원자적 단위로 커밋합니다.
   - `gh pr create`를 통해 PR 제출 (본문에 `Closes #번호` 포함).
2. **패스트 트랙 (Fast Track)**: 사용자가 커밋/푸시까지 요청한 경미한 작업
   - 즉시 구현 및 `npx tsc --noEmit` 검증.
   - 원자적 단위 커밋 및 푸시.

### 5.4 버그 수정 프로토콜 (Bug Fix Protocol)
버그 리포트 접수 시, 다음의 절차를 따릅니다. 사용자가 명시적으로 수정을 요청한 경우에는 수정 승인까지 포함된 것으로 봅니다. 단, 데이터 손상, 대규모 구조 변경, 되돌리기 어려운 변경이 예상되면 원인과 위험을 먼저 보고하고 확인을 받습니다.

1. **원인 분석**: 코드 분석을 통해 버그의 기술적 원인을 정확히 파악합니다.
2. **원인 보고**: 파악된 원인을 사용자에게 상세히 설명합니다.
3. **수정 실행**: 사용자의 요청 범위 안에서 최소 변경으로 수정합니다.
4. **검증 보고**: 재현 여부, 실행한 검증, 남은 위험을 보고합니다.

### 5.5 Issue 및 PR 템플릿 사용
- **Issue**: `bug_report`, `feature_request`, `task` 템플릿 중 성격에 맞는 것을 선택하여 상세히 기술합니다.
- **PR**: `.github/PULL_REQUEST_TEMPLATE.md`의 구조(`개요`, `주요 변경 사항`, `관련 이슈`, `체크리스트`)를 엄격히 준수합니다.
- **연동**: PR 본문에 `Closes #이슈번호`를 명시하여 작업 완료 시 이슈가 자동 닫히도록 합니다.

### ⚠️ CLI(`gh`) 사용 팁
터미널에서 PR을 생성할 때 마크다운 개행이 유지되도록 `heredoc` 구문을 권장합니다.
```bash
gh pr create --title "feat: 상점 시스템 구현" --body "$(cat <<EOF
## 개요
상점 핵심 로직 구현

## 주요 변경 사항
- Zustand 상태 관리 추가
- 업그레이드 계산 로직 분리

Closes #12
EOF
)"
```

## 🖼️ 6. 에셋 및 기타 지침 (Assets & Tools)

- **에셋 변경 기준**: 자산 추가, 교체, 아틀라스 파이프라인 변경은 `.agents/rules/06-asset-guide.md`와 `docs/ASSET_PIPELINE.md`를 따릅니다.
- **에셋 시스템**: 파일명이 ID가 되는 `PascalCase` 명명을 준수합니다.
- **UI 디자인**: 그라데이션, 유리 효과(`backdrop-blur`) 등을 사용하여 프리미엄 감성을 유지합니다.
- **이미지 생성**: 작업 중 이미지가 필요한 경우 `generate_image` 도구를 사용합니다.

## 🔎 7. 문서 활용 및 동기화 원칙 (Documentation Usage & Sync)

`docs/` 디렉터리는 프로젝트 지식의 정본 문서입니다. 에이전트는 코드 분석이나 수정 전에 관련 `docs/*` 문서를 먼저 확인하고, 문서 내용은 실제 소스 코드와 함께 검증해야 합니다.

### 7.1 코드 작업 전 문서 확인
- 작업 범위와 관련된 정본 문서를 `docs/README.md`에서 찾아 먼저 확인합니다.
- 문서만으로 판단하지 않고 `rg`로 실제 구현 파일, 타입, 상수, package script를 함께 확인합니다.
- 문서와 코드가 충돌하면 코드를 현재 동작의 기준으로 보고, 문서가 오래된 것으로 판단해 갱신 대상에 포함합니다.

### 7.2 코드 변경 시 문서 동기화
- 코드 변경이 아키텍처, 게임 루프, 데이터 모델, 상수, 저장/마이그레이션, 렌더링, 에셋 파이프라인, 배포, 개발 workflow에 영향을 주면 관련 `docs/*` 문서를 같은 변경에서 수정합니다.
- 새 기능이나 시스템을 추가할 때 기존 정본 문서의 범위에 들어가면 해당 문서에 실제 파일 경로, 명령어, 데이터 이름을 반영합니다.
- 문서에 없는 새 도메인이 생긴 경우 새 문서를 만들기보다 먼저 기존 문서 중 가장 가까운 책임의 문서에 추가합니다.
- 코드 변경과 무관한 문서 정리, 표현 개선, 대규모 재작성은 별도 요청이 없는 한 하지 않습니다.
